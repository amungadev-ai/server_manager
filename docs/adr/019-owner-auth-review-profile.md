# ADR-019 — Isolated owner-claim and session review profile

Date: 2026-11-19 (Africa/Nairobi). Tasks: CL-032/033. Status: **proposed; independent security review pending**.

## Scope and activation boundary

The user authorized the next backend batch. PR #2 has no submitted reviews; this decision does not fabricate or replace that review. Implement a concrete development candidate and its adversarial evidence, stacked on PR #4. The normal API entry point never enables the candidate, and the factory rejects review authentication in `NODE_ENV=production` or without direct TLS. No environment variable or HTTP request enables it. An internal caller must explicitly supply the review runtime and HTTPS configuration. The static Site remains a simulation. This profile does not integrate production Caddy TLS termination, installer identity, MFA, recovery or real resources.

## Proposed development policy

- Local internal claim issuance generates 256 random bits and binds the verifier to the durable installation UUID. Only the full code leaves the issuance function; only a purpose-separated SHA-256 verifier, generation, expiry and attempt count persist. There is no HTTP issuance/reset/signup endpoint. Installer printing/recovery remains CL-083/034.
- Claim lifetime: 20 minutes; at most 10 verifier failures per generation plus durable endpoint throttling. Regeneration is limited to unowned installations and invalidates earlier setup leases. Claim exchange locks the installation and claim in a PostgreSQL transaction, consumes exactly once, and creates a separate 10-minute setup lease. Lost exchange responses require deliberate local regeneration; a consumed code is never replayed to recover a secret.
- Setup leases have separate 256-bit opaque credentials, server-stored verifiers and independent random synchronizer CSRF nonces. Owner creation rechecks lease, generation, expiry and unowned state under the installation lock after password hashing; user, workspace, consumption and owned installation state commit together. Concurrent requests can create only one owner. Setup cookies are cleared on success. The response reports MFA setup required; MFA is not implemented here.
- Passwords: Argon2id using the maintained pinned `argon2` package, 19 MiB memory, two iterations, one lane, 32-byte output and independent random salt. Verification accepts only this declared PHC profile, preventing a corrupt/imported hash from selecting unbounded native cost. Minimum 15 Unicode code points, maximum 1024 UTF-8 bytes; no trimming/composition rule. Breached-password coverage, target-VPS cost tuning and MFA policy remain production review gates. Hash concurrency is bounded to two operations per runtime; no unbounded queue.
- Login uses identical errors for missing/disabled users and wrong passwords, verifies a real dummy Argon2 hash for absent users, and rechecks the current owner/hash under lock before issuing a new credential. Incoming cookie values are never adopted. A successful login revokes the supplied prior session family and creates a new family. Session records store only the purpose-separated cookie verifier; CSRF nonces are separate non-authorizing server-side state.
- Session idle lifetime: 30 minutes; absolute lifetime: 12 hours. All expiry/lease decisions use PostgreSQL time. Credentials are 256-bit random opaque values in host-only `__Host-` cookies with `Secure; HttpOnly; SameSite=Strict; Path=/`. No cookie Domain, URL token, localStorage secret or bearer/agent identity is accepted as a human session.
- Rotation revokes the old credential and creates a new credential/CSRF nonce in the same family under a family lock. Logout revokes the family under that same lock. A rotated old credential may authenticate **only logout**, with its original matching CSRF nonce and remaining absolute lifetime, so a concurrent rotation cannot escape a successful logout. It cannot read a session, rotate again or access resources. Other independent login families remain independent.
- Auth review requires actual TLS, an exact configured HTTPS Host and Origin, no authentication query parameters, JSON mutation bodies and a custom `X-Cloudlane-Request: owner-auth` header. Missing/null/sibling/cross-site Origin is rejected on mutations. Forwarded headers never establish TLS or client identity. All authenticated mutations also require a constant-time match of the session's synchronizer CSRF nonce; setup owner creation requires the setup nonce. CSRF values are returned through same-origin JSON, never through a cookie or URL.
- Throttling is durable PostgreSQL state shared across runtime instances. Global budgets are consumed before source/identity buckets to bound anonymous key growth. Fixed review budgets and bounded expiry cleanup are exercised by tests; production distributed admission, DoS and VPS benchmarks are not claimed. Audit records contain only installation/user/request IDs and action/outcome, never bodies, emails, passwords, cookies or claim material. Rate-limit rows aggregate rejected attempt counts rather than adding an unbounded audit row per blocked request.
- Public status exposes only coarse lifecycle/owner/setup booleans. Readiness always remains 503 with `authentication: review_only`; this is not production-ready authentication or infrastructure readiness. Resource/agent endpoints remain unavailable after authorization.

## Compatibility and negative evidence

Append migration `0002_owner_auth`; never edit the applied first migration. Legacy session rows have no review family/CSRF state and cannot become authenticated. Existing disabled API behavior remains unchanged. Additive session/setup CSRF response fields preserve the existing synthetic HTTP fixtures. No dashboard or reference HTML changes are required.

Required evidence includes real PostgreSQL concurrency/replay/expiry/generation/rollback/rotation/logout races, durable throttling across runtimes, real Argon2 verification and an actual HTTPS fixture whose test CA is trusted only by its clients. Fresh synthetic keys exist only in ignored test output and are never committed, packaged or uploaded; they are not deployment material. Verify Host/Origin, fake Forwarded headers, duplicate cookies, CSRF binding, fixation, expired/revoked/disabled/cross-workspace records, cookie flags on IP/custom hosts and redaction. Preserve default-disabled tests and the desktop/mobile prototype matrix.

## Review and production gates

Independent review must approve or revise this policy, MFA requirements, password/blocklist/cost choices, rate/admission limits and the trusted Caddy/transport boundary before any production activation. CL-032/033 are development candidates until that happens. Installer/local root CLI, real IP/hostname CA issuance, renewal, backup/restore and fresh-VPS evidence remain separate acceptance gates. The feature factory's explicit review switch is not a security approval.
