# ADR-023 — Restartable platform installation candidate

Status: proposed development candidate; independent security review pending
Date: 2026-11-24
Task: CL-081
Decision owner: claimant in CL-081; review pending

## Context and boundary

CL-080 provides diagnostics and single-artifact verification. CL-081 needs durable state, idempotent component installation, migration ordering and restart definitions. There is no approved publisher root, independent CL-005 approval or dedicated VPS. This batch implements and runs an **isolated review installation** using prebuilt immutable OCI images. It does not expose a production `install` command, install Docker, change host services/firewall, enable systemd units, activate owner authentication or claim public HTTPS. CL-082/083 and actual VPS acceptance remain separate.

## Decision

Add a dependency-free Go installation coordinator, a private descriptor-confined workspace, an atomic fsynced journal with nonblocking flock, independently verified platform plans, a narrow Docker driver and staged systemd definitions. CLI `review` is restricted to Linux amd64, non-root execution and a caller-owned private directory; it operates on a unique installation namespace and publishes only `127.0.0.1:<port>`. Existing Docker access is required explicitly for this development profile. It is not a general host command API.

The signed flat JSON platform plan has exactly: `schema` (1), `product` (`cloudlane-platform-review`), canonical three-part `version`, `platform` (`linux-amd64`), `database_image`, `api_image`, `caddy_image`, `schema_sha256`, `issued_at`, `expires_at`. Image references are immutable SHA-256 IDs or digest-pinned repositories; local IDs are for prebuilt CI/review images, not an operational registry release. Schema digest is SHA-256 of sorted `migration-id:checksum` lines, each terminated by LF. Independent raw Ed25519 key/fingerprint and exact version are required. Sign ASCII `CLOUDLANE-PLATFORM-PLAN-V1` + one LF + original JSON bytes; reject duplicate/unknown/missing/null fields, malformed digests/versions/targets, metadata over 16 KiB, future issuance beyond five minutes, expiry and lifetimes over 30 days. No plan-supplied shell, path, mount, service name, role, SQL, listener address or resource override exists. This is a distinct protocol from ADR-022 and the agent proposal.

The journal binds its isolated-review profile, native preflight snapshot hash, installation ID, plan hash, release and selected loopback port. The native preflight remains ineligible and does not authorize host installation; review runs on an explicitly existing Docker daemon with its separate private-resource checks. It records bounded stage attempts, status, timestamp and sanitized diagnostic code. Only successful observed postconditions mark a stage complete. Persist identity before creating secrets/resources. Generate each secret once in a separate exclusive private regular file; missing/corrupt secrets on resume fail closed. Never put secrets in journal, command arguments, image layers, logs or reports. Private 0600 environment files inject only the appropriate service credential at container creation. Docker administrators can inspect runtime environment metadata and remain trusted host administrators. A persisted database installation UUID is rechecked, preventing a silently replaced volume/database from masquerading as the original installation.

Stages: image verification, private network, database/roles, migrations/grants, API, Caddy/dashboard, aggregate internal health, staged startup units. Recheck all completed stages on every invocation. `resume` refuses completed-stage drift and directs the operator to repair. `repair` defaults to read-only diagnosis; explicit apply can restart/recreate missing **owned** containers while preserving data. Missing previously initialized database volume, changed schema history/installation UUID, foreign labels or unsafe configuration fail closed. No purge, reset, automatic downgrade or destructive rollback exists. Lost acknowledgements are resolved by observing named/labelled resources and migration history on retry. Bounded files are written via exclusive temporary file, fsync, rename and parent-directory fsync under one lock; filesystem errors never imply a completed stage.

All Docker operations use a fixed executable, explicit local Unix socket, private empty client configuration, clean child environment, typed operations, deadlines and bounded output. Never inherit Docker context/host/credentials or expose the socket to containers. Docker images/resources are verified by exact identity/configuration and installation/plan/component labels before start, reuse or removal. No host bind mounts, privileged containers, host PID/network, generic exec, arbitrary SQL or public Docker endpoint is accepted. The test cleanup only removes its own verified namespace; operational uninstall belongs to CL-084.

## Component layout

The database container owns a private bridge namespace; API, one-shot migration and Caddy containers share that **platform-only** network namespace. PostgreSQL and the unchanged normal API bind to loopback inside it. Only Caddy's internal 8080 port is mapped on host `127.0.0.1`; database/API/admin ports are not published. This preserves the existing loopback-only database configuration without relaxing the API or exposing a host-network listener. Containers have separate filesystems/PIDs, dropped capabilities, no-new-privileges, read-only root, bounded tmpfs/logging and explicit review resource limits. Limits are not a certified 1 GB profile.

PostgreSQL runs as its image's postgres UID with a uniquely owned named volume at the PostgreSQL 18 data parent. Admin, migrator and runtime passwords are distinct and persisted privately. Fixed private environment files supply each container its own role only; no password is passed in CLI arguments or committed to an image. There is no host bind mount or archive extraction. Admin uses a private in-container local socket for fixed role/grant SQL. Migration owns the schema; runtime has only database connect/schema usage and table DML, with migration-ledger writes revoked. Existing roles/passwords are never reset on retries. Migration checksum/identity and actual runtime readiness are observed after work; SQL history drift requires manual recovery.

API and dashboard images are built **in CI**, once, from the pinned lockfile and current compiled HTTP output. The target installer only inspects/pulls/runs immutable images; no npm/compiler/build executes on a customer's small VPS. The normal API authentication resolver remains disabled. The Caddy candidate serves the supplied static UI and proxies `/api/v1` on loopback; setup/login/recovery/security routes and auth mutation endpoints return 503 until trusted TLS and claim integration exist. Internal component health does not mean platform readiness: `ready_to_claim` is always false and the final state is `awaiting_tls_and_claim`, never ACTIVE.

Systemd files stage dependency ordering (Docker → DB → migration → API → Caddy), bounded restart/stop behavior and protected fixed command lines. They are checked with real `systemd-analyze verify` but never installed/enabled by this profile. Native boot, privileged custody, Docker installation/reuse, actual firewall exposure, power loss and reboot require dedicated-VPS tests and review before an operational adapter is enabled.

## Alternatives and compatibility

Running every component on the host would require root account/package/service changes before review. A generic Compose document or raw Docker JSON would enlarge the user-controlled host boundary. Sharing only the private platform network namespace keeps current loopback contracts intact; customer workloads must never join it. No HTTP contract, database migration, prototype style or authentication activation changes are required. Independent review must assess this topology, role ownership, signing/key custody, resource budgets and bootstrap/revocation/rollback policy before production use.

## Evidence

Required Go tests cover journal corruption/locking/symlinks/permissions/interrupted writes, signature/pin/time/plan validation, retry/lost-ack/identity preservation, drift, dry-run and strict Docker ownership/configuration. A separate mandatory Ubuntu job builds real API/Caddy images, runs real PostgreSQL migrations and Caddy HTTP routing, exercises rerun/interruption/resume/repair and checks staged units. No fake service response counts as that integration evidence. Existing SQL, browser and 40 source-prototype comparisons remain required. Exact source/run/results and remaining limitations go in CL-081 and the batch report.
